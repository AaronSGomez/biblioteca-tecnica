Resumen Ejecutivo y Arquitectura del Sistema

Este informe documenta el diseño y la implementación del motor backend de Novapay, desarrollado con Spring Boot 3.2 y Java 21. La aplicación fue concebida como un middleware centralizado capaz de recibir transacciones comerciales emitidas por dispositivos TPV cliente (tablets Android, pantallas táctiles e interfaces móviles en Flutter) y procesar de forma transparente la firma digital, el encadenamiento de huellas criptográficas SHA-256 y el envío regulatorio hacia las distintas administraciones tributarias españolas.

La elección de Java 21 permite utilizar hilos virtuales (Project Loom) para atender de forma concurrente cientos de conexiones REST simultáneas provenientes de cajas registradoras sin penalización en memoria, mientras que Spring Framework proporciona abstracción para la persistencia relacional relacional con JPA/Hibernate y el empaquetado de servicios web SOAP mediante Spring WS.

Arquitectura Capa por Capa (Spring Boot)

El backend aplica el principio de responsabilidad única. Cuando una aplicación cliente emite una venta, el paquete JSON ingresa por la capa de controladores REST, se transforma a entidades del dominio, se procesa en el servicio de negocio garantizando la integridad de la base de datos y finalmente se deriva al módulo de transporte correspondiente.

@RestController InvoiceController

Punto de entrada de peticiones REST HTTP. Desacopla la interfaz de usuario de las reglas tributarias del servidor. Recibe el DTO firmado por la sesión del cajero y delega la ejecución al servicio transaccional. 

@PostMapping("/api/v1/invoices")
public ResponseEntity<InvoiceResult> create(@Valid @RequestBody InvoiceDTO invoice) {
    // 1. Recepción y validación estricta del Payload JSON
    // 2. Delegación síncrona al motor transaccional
    InvoiceResult result = invoiceService.processInvoice(invoice);
    return ResponseEntity.status(HttpStatus.CREATED).body(result);
}

@Service InvoiceService

Orquestador de lógica de negocio y transaccionalidad `@Transactional`. Obtiene el último hash guardado en base de datos para garantizar la secuencia ininterrumpida, genera la huella criptográfica actual y registra la factura en estado `PENDING`. 

@Transactional
public InvoiceResult processInvoice(InvoiceDTO data) {
    // 1. Obtención del hash inmediatamente anterior en el libro registro
    String prevHash = repository.findTopByOrderByIdDesc()
                                .map(InvoiceEntity::getChainHash)
                                .orElse("00000000000000000000000000000000");
    
    // 2. Cálculo de la nueva huella SHA-256 encadenada
    String newHash = hashGenerator.calculateHash(data, prevHash);
    
    // 3. Firma digital utilizando la clave privada RSA
    String signature = signer.sign(newHash, keyManager.getPrivateKey());
    
    // 4. Inserción obligatoria en PostgreSQL en estado PENDING
    InvoiceEntity entity = repository.save(new InvoiceEntity(data, newHash, signature, "PENDING"));
    
    // 5. Publicación de evento asíncrono para transmisión a Hacienda
    eventPublisher.publishEvent(new FiscalSendEvent(entity.getId()));
    return new InvoiceResult(entity.getInvoiceNumber(), newHash, "ACCEPTED_LOCAL");
}

Componentes Criptográficos (`HashGenerator` & `Signer`)

Módulo encargado del cumplimiento estricto del algoritmo SHA-256 de VeriFactu y la firma PKCS#1 v1.5 / XAdES.

  • HashGenerator.java: Concatena NIF emisor, número de serie, fecha/hora ISO, importe total y hash anterior.
  • Signer.java: Aplica algoritmo SHA256withRSA sobre los datos normalizados.
  • KeyManager.java: Carga dinámica del almacén PKCS#12 (.p12) montado como volumen Docker.
⚠️ Medida de Seguridad: El certificado digital nunca se empaqueta dentro del binario JAR. Se inyecta en tiempo de ejecución en la ruta segura /app/certs/certificado.p12.

Persistencia Relacional (PostgreSQL)

Definición DDL del esquema relacional. Almacena las facturas emitidas, los identificadores de cadena criptográfica y la respuesta (CSV) devuelta por la Agencia Tributaria. 

CREATE TABLE invoices (
    id BIGSERIAL PRIMARY KEY,
    invoice_number VARCHAR(50) NOT NULL UNIQUE,
    issue_date TIMESTAMP NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    chain_hash VARCHAR(64) NOT NULL,       -- Huella SHA-256 actual
    prev_hash VARCHAR(64) NOT NULL,        -- Huella del registro inmediatamente anterior
    signature_data TEXT NOT NULL,          -- Bloque de firma digital X.509
    status VARCHAR(20) DEFAULT 'PENDING',  -- PENDING, SENT, REJECTED
    aeat_csv VARCHAR(100),                 -- Código Seguro de Verificación oficial
    retry_count INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Sistema de Resiliencia y Cola Asíncrona

En el punto de venta (TPV) no es admisible bloquear la pantalla de cobro ni hacer esperar al cliente final si los servidores de la Agencia Tributaria están caídos o sufren latencia. Por ello, Novapay aplica un principio de resiliencia estricto: la transacción se guarda primero en la base de datos PostgreSQL local en estado PENDING y se responde un estado OK_LOCAL a la caja registradora en menos de 50 milisegundos.

La retransmisión hacia los servidores de Hacienda la gestiona un hilo asíncrono secundario programado con el algoritmo de **Espera Incremental (Exponential Backoff)**. Esto evita saturar la red con peticiones consecutivas durante una interrupción de servicio.

Estrategia Exponential Backoff

Intervalos de espera exponenciales entre intentos (1s, 2s, 4s, 8s, 16s...) para prevenir tormentas de peticiones.

Reglas de Negocio de Resiliencia

  • 1 Persistencia Asentada Primero: Jamás se realiza una llamada remota sin haber asegurado el registro de la factura en PostgreSQL.
  • 2 Respuesta Inmediata al TPV: La caja registradora imprime el ticket con el código QR y continúa vendiendo sin bloqueo.
  • 3 Confirmación CSV Oficial: Al recibir HTTP 200 OK y el Código Seguro de Verificación (CSV), se actualiza el estado del registro a SENT.
  • 4 Alerta Operativa: Tras 10 intentos fallidos, se genera un log de auditoría pero NO se elimina el registro de la base de datos.

Infraestructura de Contenedores Docker

Toda la solución se encapsula mediante Docker Compose para garantizar portabilidad. Nginx opera como Proxy Inverso perimetral realizando la terminación SSL HTTPS (certificados Let's Encrypt), filtrando peticiones maliciosas (límite estricto de 56KB por cuerpo para evitar desbordamientos de búfer) y reenviando el tráfico limpio a Spring Boot en el puerto local 8080.

Checklist Operaciones y Despliegue

Enlace dinámico de la IP pública mediante DuckDNS para permitir conectividad HTTPS desde las tablets TPV.

2. Certificados TLS Let's Encrypt

Generación y renovación automática mediante Certbot. Previene bloqueos SSL en clientes móviles.

3. Aislamiento de Volúmenes de Datos

Persistencia fuera del contenedor mediante - ./pgdata:/var/lib/postgresql/data para respaldos sencillos.

4. Migración sin Interrupción a Cloud

Traspaso directo del archivo docker-compose.yml a AWS/Cloud en menos de 15 minutos.
